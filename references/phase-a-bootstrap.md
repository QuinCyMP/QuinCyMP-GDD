## ก่อนเขียนอะไรทั้งสิ้น: ล็อก 5 ข้อนี้ให้ได้ก่อน

อย่าเริ่มเขียนเอกสารจนกว่าจะได้คำตอบทั้ง 5 ข้อจากผู้ใช้ ถามทีละชุด อย่ายิงรวดเดียว 20 คำถาม
ถ้าผู้ใช้ตอบกว้าง ๆ ให้เสนอตัวเลือกที่เจาะจง 2–3 ทางให้เลือก แล้วเขียนต่อจากทางที่เลือก
เหตุผลที่ต้องล็อกก่อน: ทุกหัวข้อที่เหลือของเอกสารเป็น**ผลสืบเนื่อง**ของห้าข้อนี้
ถ้าเขียนไปก่อนแล้วค่อยกลับมาแก้ ต้องรื้อทั้งฉบับ

**1. Core loop 30 วินาที**
ผู้เล่นกดอะไร เห็นอะไรตอบกลับ ได้อะไร แล้ววนกลับมาทำซ้ำเพราะอะไร — ต้องเล่าเป็นการกระทำจริง
ไม่ใช่ชื่อระบบ ("สู้ ดรอปของ อัปเกรด" ไม่ผ่าน เพราะยังไม่รู้ว่าการสู้หนึ่งครั้งใช้เวลากี่วินาที
ผู้เล่นตัดสินใจอะไรระหว่างนั้น และของที่ดรอปเปลี่ยนการเล่นครั้งถัดไปอย่างไร)

**2. The One Thing — จุดต่างข้อเดียว**
เขียนให้ได้ในรูปประโยคนี้:
> "ในเกมนี้ผู้เล่น___ได้ ซึ่ง [เกมที่มีอยู่จริง 2–3 ชื่อ] ทำไม่ได้ เพราะระบบของเขา___"

ถ้าเติมประโยคนี้ไม่ได้ เกมยังไม่มีเหตุผลในการมีอยู่ และเอกสารจะขายไม่ออกแน่นอน
หนึ่งข้อพอ — สองข้อขึ้นไปแปลว่ายังไม่ได้เลือก

**3. ทำไมต้องเป็น MMO / มีผู้เล่นอื่น**
ถ้าตัดผู้เล่นคนอื่นออกแล้วเกมยังสนุกเท่าเดิม แสดงว่านี่คือเกม single-player ที่มีคนอื่นวิ่งผ่าน
นี่คือจุดที่เอกสาร MMO ของมือสมัครเล่นพังบ่อยที่สุด ต้องระบุให้ได้ว่าผู้เล่นคนอื่น**จำเป็น**
ต่อระบบไหน: เศรษฐกิจต้องมีคนผลิต-คนซื้อ / เนื้อหาต้องใช้หลายคน / ความหมายมาจากการแข่งหรือชื่อเสียง
/ โลกเปลี่ยนตามการกระทำรวมหมู่

**4. ผู้เล่นเป้าหมายที่มีตัวตนจริง**
ไม่ใช่ "คนชอบเกม MMO อายุ 18–35" แต่เป็น "คนที่ตอนนี้เล่น [เกมจริง] อยู่ และหงุดหงิดกับ___
จนเลิกเล่นไป" — ผู้ซื้อทุกประเภทจะถามคำถามนี้ และคำตอบที่เจาะจงคือสิ่งที่แยกเอกสารที่ขายได้
ออกจากเอกสารที่ถูกปิดทิ้งตั้งแต่หน้าสอง

**5. Vertical slice ที่คนเดียวพิสูจน์ได้**
ชิ้นเล็กที่สุดที่เล่นแล้วรู้สึกถึง The One Thing ได้จริง — ใหญ่แค่ไหน ใช้เวลากี่เดือน ตัดอะไรออกบ้าง
แม้ผู้ใช้จะยังไม่ลงมือสร้าง ข้อนี้ก็ต้องมีในเอกสาร เพราะมันคือสิ่งที่ผู้ซื้อใช้ประเมินว่า
ดีไซน์นี้ "พิสูจน์ได้" หรือเป็นแค่ความคิด

## ชุดเอกสารที่ผลิต *(เฟส A เท่านั้น)*

🔴 **นี่คือข้อเสนอ ไม่ใช่คำสั่ง** — ถ้าโปรเจกต์มีโครงของตัวเองแล้ว **ใช้ของเขา**
ชื่อไฟล์ที่ผิดแต่มีลิงก์ถึงกันครบ ดีกว่าชื่อไฟล์ที่ถูกแต่ต้องไล่แก้ลิงก์ทั้งคลัง

ใช้สคริปต์ตั้งโครงก่อน แล้วค่อยเติมเนื้อหาทีละไฟล์:

```bash
python scripts/scaffold_gdd.py <โฟลเดอร์ปลายทาง> --title "ชื่อเกม"
```

โครงที่ได้:

```
design/

├── 01-vision.md           pillars, The One Thing, ผู้เล่นเป้าหมาย, ทำไมต้อง MMO
├── 02-core-loops.md       loop 30 วินาที / 1 ชั่วโมง / 1 สัปดาห์ / ตลอดชีวิตตัวละคร
├── 03-world.md            ขนาดโลก ความหนาแน่น การเดินทาง การแบ่งโซน

├── 05-combat.md           จังหวะ ตัวเลข role การตัดสินใจต่อวินาที
├── 06-economy.md          faucet/sink ตลาดผู้เล่น ตารางราคา

├── 09-monetization.md     รูปแบบรายได้ และผลกระทบย้อนกลับต่อ design
```

ไม่จำเป็นต้องเขียนครบทุกไฟล์ในครั้งเดียว ถามผู้ใช้ว่าอยากลุยไฟล์ไหนก่อน
ลำดับที่ได้ผลที่สุดคือ `01 → 02 → 12 → 06` (วิสัยทัศน์ → ลูปหลัก → ขอบเขต → เศรษฐกิจ)
เพราะสี่ไฟล์นี้บีบให้ตัดสินใจเรื่องยากที่สุดก่อน ส่วน `00-one-pager.md` เขียน**ท้ายสุด**
เพราะการย่อสิ่งที่ยังไม่ตัดสินใจให้เหลือหน้าเดียวเป็นไปไม่ได้

## ข้อจำกัดที่ต้องบอกผู้ใช้ตรง ๆ (ครั้งเดียว ไม่ต้องย้ำ)

MMORPG open world คือแนวเกมที่แพงที่สุดที่มนุษย์สร้าง คนเดียวสร้างจนจบไม่ได้ —
ไม่ใช่เพราะฝีมือ แต่เพราะมันต้องใช้**โรงงานผลิตเนื้อหา**ที่ป้อนผู้เล่นได้เร็วกว่าที่ผู้เล่นกิน

แต่ทางที่ทำได้จริงมีอยู่ และเอกสารควรเลือกทางใดทางหนึ่งอย่างชัดเจน:
- **ออกแบบเต็ม ขายหรือส่งต่อให้ทีมใหญ่สร้าง** — ทางที่ผู้ใช้เลือกอยู่ ให้เอกสารสมบูรณ์พอที่คนอื่นสร้างต่อได้
- **ย่อ scope ให้เหลือสิ่งที่ทีมเล็กทำได้** — MMO เล็ก (เพดาน 100–500 คน), โลกเดียวไม่ใช่หลาย shard,
  เนื้อหาที่ผู้เล่นสร้างกันเอง, systemic แทน handcrafted — ให้เสนอทางนี้ไว้ใน `12-scope-roadmap.md`
  เป็นทางเลือกสำรอง เพราะมันคือสิ่งที่ทำให้ vertical slice เกิดขึ้นจริงได้
- **ทำ prototype พิสูจน์ The One Thing แล้วค่อยหาทีม** — เพิ่มมูลค่าเอกสารมากที่สุด

พูดเรื่องนี้**หนเดียวตอนเริ่ม** แล้วทำงานต่อตามที่ผู้ใช้เลือก อย่าย้ำซ้ำทุกไฟล์
และเมื่อพูดไปแล้ว ให้ถือว่าผู้ใช้รับทราบข้อจำกัดแล้ว — หลังจากนั้นหน้าที่คือช่วยให้
ไอเดียของเขาออกมาดีที่สุดในแบบของมัน ไม่ใช่คอยเตือนเรื่องความเป็นไปได้ทุกครั้งที่เขาเสนออะไรใหม่

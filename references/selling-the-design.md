# ทำให้เอกสารออกแบบขายได้หรือส่งต่อได้จริง

> ⚠️ **ขนาดทีม:** คำแนะนำแบบ "ทีมเล็ก / นักพัฒนาเดี่ยว" ในไฟล์นี้ใช้เมื่อโปรเจกต์เป็นทีมเล็กเท่านั้น · ถ้าโปรเจกต์เป็นทีมระดับองค์กรหรือ AAA ให้ถือเป็นทางเลือก ไม่ใช่ข้อจำกัด และห้ามใช้เป็นเหตุผลตัดไอเดีย (ดูหัวไฟล์ SKILL.md)

อ่านเมื่อเขียนไฟล์ใน `pitch/` หรือเมื่อผู้ใช้ถามเรื่องขายไอเดีย หาพับลิชเชอร์ ลิขสิทธิ์

## ความจริงข้อแรกที่ต้องบอกผู้ใช้อย่างตรงไปตรงมา

**ตลาดของ "เอกสารออกแบบเปล่า ๆ" แทบไม่มีอยู่จริง** สตูดิโอเกือบทั้งหมดปฏิเสธรับไอเดีย
จากคนนอกเป็นนโยบาย เพื่อกันคดีความเรื่อง "ฉันคิดก่อน" และเพราะไอเดียไม่ใช่สิ่งที่เขาขาด —
สิ่งที่ขาดคือกำลังการผลิตและความมั่นใจว่ามันจะเวิร์ก

นี่ไม่ใช่เหตุผลให้เลิก แต่เป็นเหตุผลให้เลือกทางที่มีตลาดจริง มีอยู่ 5 ทาง:

| ทาง | ขายอะไรจริง ๆ | ความเป็นไปได้ | สิ่งที่ต้องมีเพิ่มจาก GDD |
|---|---|---|---|
| **GDD + prototype เล่นได้** | หลักฐานว่าสนุกจริง | สูงที่สุด | vertical slice ที่เล่นได้ 10–20 นาที |
| **IP + art bible** | โลก ตัวละคร บรรยากาศ | กลาง | งานศิลป์ที่มีเอกลักษณ์ + เรื่องราวที่สมบูรณ์ |
| **เข้าร่วมทีมในฐานะดีไซเนอร์** | ตัวคุณ + เอกสารเป็นพอร์ต | สูง | เอกสารที่โชว์วิธีคิด ไม่ใช่แค่ผลลัพธ์ |
| **ขายระบบ/สเปกเฉพาะส่วน** | ระบบเดียวที่ออกแบบละเอียดมาก | กลาง | spec + ตารางข้อมูลที่ implement ตามได้ทันที |
| **หาผู้ร่วมทีมมาสร้างด้วยกัน** | วิสัยทัศน์ + scope ที่น่าเชื่อ | สูง | roadmap ที่พิสูจน์ว่าคุณเข้าใจข้อจำกัด |

**สิ่งที่เพิ่มมูลค่าเอกสารมากที่สุด เรียงตามผลจริง:**
1. prototype ที่เล่นได้ แม้จะเป็นกล่องสี่เหลี่ยม — พลิกจาก "ไอเดีย" เป็น "ของ"
2. หลักฐานว่ามีคนอยากเล่น — ยอด wishlist, สมาชิก Discord, คลิปที่มีคนดู
3. ตารางข้อมูลที่ครบ — แสดงว่าคิดจบแล้ว ไม่ใช่คิดแค่เปลือก
4. หัวข้อความเสี่ยงที่ซื่อสัตย์ — คนซื้อมองหาคนที่รู้ตัว
5. scope ที่เล็กพอจะเชื่อได้

## ผู้ซื้อสามแบบ ต้องการคนละอย่าง

เขียน `pitch/buyer-brief.md` แยกตามคนที่จะส่งให้ อย่าส่งฉบับเดียวกันให้ทุกคน

### แบบ A — พับลิชเชอร์ / นักลงทุน
เขาถามในใจว่า "เงินที่ใส่ไป จะกลับมาเท่าไร เมื่อไร ความเสี่ยงอะไร"

ต้องมี:
- ตลาดเป้าหมายเป็นตัวเลข — เกมใกล้เคียงขายได้เท่าไร ราคาเท่าไร รีวิวกี่อัน
- งบและระยะเวลาจนถึงวันปล่อย
- โมเดลรายได้และประมาณการแบบอนุรักษ์นิยม
- ทีม — ใครทำได้จริง (จุดอ่อนที่สุดของนักพัฒนาเดี่ยว ต้องมีแผนรับมือ)
- ความเสี่ยงและแผนลด

อย่าใส่: รายละเอียดระบบยาว ๆ เขาไม่อ่าน

### แบบ B — สตูดิโอหรือคนซื้อ IP
เขาถามว่า "เอาไปสร้างต่อได้เลยไหม หรือต้องออกแบบใหม่หมด"

ต้องมี:
- ระบบที่ระบุละเอียดพอให้โปรแกรมเมอร์เริ่มได้โดยไม่ต้องถาม
- ตารางข้อมูลใน `data/`
- ข้อกำหนดทางเทคนิคที่ design นี้เรียกร้อง
- ความชัดเจนว่า**ใครเป็นเจ้าของงานนี้** — ถ้าเคยจ้างคนวาดรูปหรือเคยร่วมคิดกับเพื่อน
  ต้องเคลียร์ก่อน เพราะความไม่ชัดเจนของสิทธิ์ทำให้ดีลล่มบ่อยกว่าคุณภาพงาน

### แบบ C — ผู้ร่วมทีม / co-founder
เขาถามว่า "ฉันจะเสียเวลาสองปีกับคนนี้ไหม"

ต้องมี:
- วิสัยทัศน์ที่ชัดจนเขาเห็นภาพเดียวกับคุณ
- scope ที่เล็กพอจะเชื่อว่าจบได้
- บทบาทที่ชัดว่าเขาทำอะไร คุณทำอะไร ใครตัดสินใจสุดท้าย
- ข้อตกลงเรื่องสัดส่วนและสิทธิ์ตั้งแต่วันแรก ก่อนเริ่มทำงาน

## ลำดับการส่ง — อย่าส่งทั้งฉบับเป็นอันแรก

1. **อีเมลสั้น + logline** (5 บรรทัด) → ดูว่าเขาตอบไหม
2. **one-pager** → ถ้าเขาสนใจ
3. **คุยกัน** → ให้เขาถาม
4. **เอกสารเต็ม** → หลังจากมีความสัมพันธ์แล้ว และหลังจากคุยเรื่องข้อตกลงเบื้องต้น

เหตุผล: เอกสาร 40 หน้าที่ส่งไปกับอีเมลแรกจะไม่ถูกเปิด และคุณเสียโอกาสที่จะรู้ว่า
เขาปฏิเสธเพราะอะไร

## เรื่องสิทธิ์ — แนวปฏิบัติทั่วไป ไม่ใช่คำแนะนำทางกฎหมาย

สิ่งเหล่านี้เป็นแนวปฏิบัติที่ใช้กันในวงการ สำหรับสัญญาจริงหรือดีลที่มีเงินก้อน
ควรให้ทนายที่ทำด้านทรัพย์สินทางปัญญาดู เพราะรายละเอียดต่างกันไปตามประเทศ

- **ลิขสิทธิ์คุ้มครองการแสดงออก ไม่คุ้มครองไอเดีย** — "MMO ที่ของผุพังตามเวลา" ไม่มีใครเป็นเจ้าของได้
  แต่เอกสาร ข้อความ ภาพ ชื่อเฉพาะ และตารางข้อมูลที่คุณเขียน เป็นของคุณตั้งแต่เขียนเสร็จ
- **สร้างหลักฐานวันที่** — เก็บงานใน git ที่มี commit history หรือส่งอีเมลหาตัวเอง
  เป็นหลักฐานว่ามีงานนี้อยู่ ณ วันนั้น ทำฟรีและมีประโยชน์
- **NDA มีประโยชน์จำกัด** — สตูดิโอใหญ่มักไม่เซ็นก่อนดูงาน คนที่ยอมเซ็นมักเป็นรายเล็ก
  อย่าให้การไม่มี NDA มาหยุดการคุย แต่ก็อย่าส่งของสำคัญที่สุดไปก่อนมีความสัมพันธ์
- **ระวังสิ่งที่ไม่ใช่ของคุณ** — ภาพอ้างอิงจากเน็ต งานที่ AI สร้าง ชื่อที่ซ้ำเครื่องหมายการค้า
  ต้องเคลียร์ก่อนเอกสารออกสู่สายตาคนซื้อ ให้ระบุแหล่งที่มาของทุกภาพในเอกสาร
- **รูปแบบดีลที่พบจริง** — ขายขาดเกิดน้อยมาก ที่เจอบ่อยคือ จ้างเป็นดีไซเนอร์,
  ส่วนแบ่งรายได้, เครดิต + ค่าตอบแทนตามหมุดหมาย ตั้งความคาดหวังตามนี้

## โครง pitch deck (10–12 สไลด์)

| # | สไลด์ | เนื้อหา |
|---|---|---|
| 1 | ชื่อเกม + logline | ประโยคเดียว ภาพเดียว |
| 2 | ปัญหา / ช่องว่าง | ผู้เล่นเป้าหมายหงุดหงิดกับอะไรในเกมที่มีอยู่ |
| 3 | The One Thing | จุดต่างข้อเดียว พร้อมภาพหรือคลิป |
| 4 | Core loop | ผู้เล่นทำอะไรวนซ้ำ |
| 5 | โลกและบรรยากาศ | ภาพศิลป์ ไม่ใช่ตัวหนังสือ |
| 6 | ระบบหลัก 3 ระบบ | สั้น ๆ ระบบละ 2 บรรทัด |
| 7 | ตลาดและเกมเทียบเคียง | ตัวเลขยอดขาย/ผู้เล่นของเกมใกล้เคียง |
| 8 | โมเดลรายได้ | |
| 9 | Scope และไทม์ไลน์ | vertical slice → เวอร์ชันแรก |
| 10 | ทีมและสถานะปัจจุบัน | มีอะไรแล้วบ้าง |
| 11 | สิ่งที่ต้องการ | ขอเงินเท่าไร ขอคนแบบไหน ขออะไร — ต้องชัด |

สไลด์ 11 คือสไลด์ที่คนลืมใส่บ่อยที่สุด และเป็นเหตุผลที่การประชุมจบแบบไม่มีอะไรเกิดขึ้น

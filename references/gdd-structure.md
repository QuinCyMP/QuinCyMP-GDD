The One Thing ข้อเดียว + เทียบกับเกมที่มีอยู่จริง 2 ชื่อ

world size · session length · time to endgame · concurrency ต่อ zone

## 01 Vision

ต้องมี:
- **Pillars 3 ข้อ** — หลักตัดสินใจที่ใช้ตอบว่า "ฟีเจอร์นี้เข้าไหม" ต้องคมพอที่จะ*ปฏิเสธ*ของดี ๆ ได้
  pillar ที่ปฏิเสธอะไรไม่ได้เลย (เช่น "สนุก", "มีคุณภาพ") ไม่ใช่ pillar
- **The One Thing** ในรูปประโยคเปรียบเทียบกับเกมจริง
- **ผู้เล่นเป้าหมาย** — เล่นอะไรอยู่ตอนนี้ หงุดหงิดกับอะไร ใช้เวลาเล่นครั้งละเท่าไร
- **ทำไมต้องมีผู้เล่นอื่น** — ระบบไหนพังถ้าเล่นคนเดียว
- **อารมณ์เป้าหมาย** — ผู้เล่นควรรู้สึกอะไรใน 10 นาทีแรก / ชั่วโมงที่ 10 / ชั่วโมงที่ 100

ถามผู้ใช้:
- เกมไหนที่คุณเล่นแล้วคิดว่า "ถ้ามันทำแบบนี้แทนคงดี"
- ถ้าต้องตัดทุกอย่างเหลือระบบเดียว เก็บอะไร
- ผู้เล่นเล่าเกมนี้ให้เพื่อนฟังยังไงด้วยประโยคเดียว

ตัวอย่าง pillar ที่ใช้ได้จริง:
> **"ทุกอย่างเสื่อมสภาพ"** — ไม่มีไอเทมถาวร ไม่มีฐานถาวร ไม่มีอันดับถาวร
> ปฏิเสธ: legendary item ที่เก็บไว้ตลอดกาล, achievement ถาวร, ที่ดินซื้อขาดหนึ่งครั้งจบ

## 02 Core loops

ลูปสี่ชั้น แต่ละชั้นต้องมีเวลาจริงกำกับ:

| ชั้น | ช่วงเวลา | ต้องตอบว่า |
|---|---|---|
| **Moment** | 1–30 วินาที | กดอะไร เห็นอะไรตอบกลับ ตัดสินใจอะไร |
| **Session** | 20–90 นาที | เปิดเกมมาทำอะไรเป็นอย่างแรก ปิดเกมตอนไหนถึงรู้สึกว่าคุ้ม |
| **Week** | 5–15 ชั่วโมง | อะไรทำให้กลับมาวันพรุ่งนี้ ที่ไม่ใช่แค่ daily quest |
| **Lifetime** | 100–1000 ชั่วโมง | อะไรคือ "จบ" และหลังจากนั้นยังมีอะไร |

เขียนแต่ละชั้นเป็น **ลำดับการกระทำจริง** ไม่ใช่ชื่อระบบ:
> ❌ "ผู้เล่นสู้ ได้ของ อัปเกรด แล้วสู้ต่อ"
> ✅ "เจอ mob 3 ตัว → เลือกว่าจะดึงทีละตัว (ปลอดภัย 25 วินาที) หรือดึงทั้งกลุ่ม (เสี่ยง แต่ 12 วินาที
> และได้ bonus loot จาก multi-kill) → ตัดสินใจนี้ซ้ำทุก ๆ 20 วินาที และเปลี่ยนไปตาม HP ที่เหลือ"

**หัวใจ:** ทุกลูปต้องมี*การตัดสินใจ*ที่ผู้เล่นทำ ลูปที่ไม่มีการตัดสินใจคือแรงงาน

## 04 Progression

ต้องตอบ 4 คำถาม:
1. ผู้เล่นแข็งแกร่งขึ้นด้วยอะไร — เลเวล / เกียร์ / สกิล / ความรู้ของตัวผู้เล่นเอง / ชื่อเสียงในโลก
2. **Vertical หรือ horizontal** — เพิ่มพลัง (ต้องมีเนื้อหาใหม่ป้อนตลอด) หรือเพิ่มทางเลือก (ทีมเล็กทำได้จริงกว่ามาก)
3. มี cap ไหม ถึง cap แล้วยังโตทางไหนได้
4. ผู้เล่นใหม่ที่เข้ามาปีที่ 2 ไล่ทันคนเก่าไหม และ**ควร**ไล่ทันไหม

ต้องมีตัวเลข: xp curve (ใส่ `data/xp-curve.csv`), ชั่วโมงถึงเลเวลสุดท้าย, power ratio ระหว่างผู้เล่นใหม่กับ endgame

กับดักของทีมเล็ก: vertical progression ต้องมี tier ใหม่ทุก ๆ 3–6 เดือน ไม่งั้นผู้เล่นหมดเป้าหมาย
ถ้าไม่มีทีมผลิตเนื้อหา ให้เอนไป horizontal + prestige ที่ผู้เล่นสร้างความหมายกันเอง

## 05 Combat

ต้องมีตัวเลข ไม่งั้นถือว่าไม่ได้ออกแบบ:
- **TTK** — ฆ่า mob ธรรมดากี่วินาที / ผู้เล่นต่อผู้เล่นกี่วินาที
- **GCD / จังหวะ** — กดปุ่มได้ถี่แค่ไหน กี่ปุ่มที่ใช้จริงในหนึ่งการต่อสู้
- **การตัดสินใจต่อวินาที** — ช้า (tab-target, วางแผน) หรือเร็ว (action, สะท้อนกลับ) — ข้อนี้ตัดสิน netcode ทั้งหมด
- **ความหมายของความตาย** — เสียอะไร เดินกลับนานแค่ไหน

คำถามชี้ขาดสำหรับ MMO: **tab-target หรือ action combat**
action ต้องการ tick rate สูง ทำให้ค่า server แพงขึ้นหลายเท่าและจำกัดจำนวนคนต่อพื้นที่
tab-target ทนเลทได้ รองรับคนเยอะกว่า และเป็นเหตุผลที่ MMO ใหญ่ ๆ ยังใช้อยู่
ต้องเขียนเหตุผลของการเลือกลงเอกสาร เพราะคนที่รับไปสร้างต่อจะถามข้อนี้เป็นข้อแรก

## 08 Endgame / live ops

คำถามเดียวที่สำคัญ: **คนเล่นครบ 300 ชั่วโมงแล้วเปิดเกมมาทำอะไร**

ตัวเลือกที่มีจริง (เลือกได้มากกว่าหนึ่ง แต่ต้องบอกว่าอันไหนเป็นหลัก):
| รูปแบบ | ต้องการอะไรจากทีม | เหมาะกับทีมเล็กไหม |
|---|---|---|
| Raid / dungeon tier ใหม่ | เนื้อหาใหม่ทุก 2–3 เดือน | ❌ แพงที่สุด |
| PvP แข่งขัน / ranked | บาลานซ์ต่อเนื่อง + ระบบกันโกง | ⚠️ บาลานซ์กินเวลามาก |
| เศรษฐกิจและการค้า | ดูแลตัวเลข ไม่ต้องผลิต asset | ✅ |
| การเมือง ดินแดน สงครามกิลด์ | ระบบครั้งเดียว ผู้เล่นผลิตดราม่าเอง | ✅ ทางที่คุ้มที่สุด |
| Housing / creation | เครื่องมือสร้าง + พื้นที่เก็บ | ✅ ถ้าทำเครื่องมือดี |
| Procedural / roguelike ซ้ำได้ | ระบบสุ่มที่ออกแบบดี | ✅ |

**ต้องระบุอัตราการบริโภค** — ผู้เล่นหนักกินเนื้อหาที่ใช้เวลาสร้าง 3 เดือน หมดใน 2 สัปดาห์
เอกสารต้องเขียนอัตรานี้ตรง ๆ แล้วบอกว่าอะไรอุดช่องว่าง

## 09 Monetization

เลือกหนึ่ง: **buy-to-play / subscription / free-to-play** แล้วเขียน**ผลย้อนกลับต่อ design**
เพราะโมเดลรายได้เปลี่ยนดีไซน์ ไม่ใช่แค่วิธีเก็บเงิน:

- **B2P** — ไม่มีรายได้ต่อเนื่อง ต้องมี DLC หรือขาย cosmetic; ออกแบบให้ผู้เล่นเลิกเล่นได้อย่างพอใจ
- **Subscription** — ต้องป้อนเนื้อหาสม่ำเสมอไม่งั้นคนยกเลิก; เหมาะกับเกมที่เศรษฐกิจต้องสะอาด
- **F2P** — ต้องออกแบบ*จุดที่คนยอมจ่าย*ตั้งแต่แรก ไม่ใช่แปะร้านค้าทีหลัง; เสี่ยง pay-to-win
  ซึ่งทำลายเศรษฐกิจผู้เล่นได้ทั้งระบบ

เขียนให้ชัดว่า **อะไรที่จะไม่ขายเด็ดขาด** — ข้อนี้มีค่าทางการขายเอกสาร เพราะแสดงว่าเข้าใจว่า
ความไว้ใจของผู้เล่นคือทรัพย์สิน

## 10 Art & audio

ไม่ใช่แค่ "สไตล์ไหน" แต่ต้องมี **งบทางเทคนิค** เพราะมันคือสิ่งที่กำหนดว่าทีมจะผลิตทันไหม:
- จำนวน asset ที่ต้องมีสำหรับ vertical slice (ตัวละคร / mob / prop / ชุดเกราะ)
- ข้อจำกัดที่ทำให้ผลิตเร็ว: จำนวน texture set, ระบบสีแบบเปลี่ยนได้, modular kit
- สไตล์ที่เลือกเพราะ*ผลิตง่ายกับทีมเท่านี้* — stylized ราคาถูกกว่า realistic หลายเท่า
- เสียง: กี่แทร็ก กี่ SFX เป็นอย่างน้อย

## 11 Tech assumptions

ไฟล์นี้คือสิ่งที่ทำให้เอกสาร "ส่งต่อได้" — บอกว่า design นี้**เรียกร้องอะไร**จากฝั่งเทคนิค
โดยไม่ต้องเลือก engine ให้:
- ผู้เล่นที่ต้องเห็นพร้อมกันในพื้นที่เดียว (กี่คน)
- tick rate ที่ระบบต่อสู้ต้องการ
- ข้อมูลที่ต้องคงอยู่ถาวร (inventory, ที่ดิน, ความสัมพันธ์, สภาพโลก)
- อะไรที่ server ต้องตัดสิน และอะไรที่ client ตัดสินได้ (ทุกอย่างที่แลกเป็นเงินได้ = server เท่านั้น)
- ขนาดโลกและวิธีโหลด (streaming / zone loading / instance)

เขียนเป็น requirement ไม่ใช่ solution — คนที่รับไปสร้างจะเลือกวิธีเอง แต่ต้องรู้ข้อจำกัด

## 12 Scope & roadmap

สามส่วน:
1. **Vertical slice** — เล็กที่สุดที่พิสูจน์ The One Thing; ระบุพื้นที่ จำนวนระบบ จำนวน asset เวลาที่ใช้
2. **ลำดับการสร้าง** — ระบบไหนต้องมาก่อน เพราะระบบอื่นพึ่งมัน
3. **สิ่งที่ตัดออกในเวอร์ชันแรก** พร้อมเหตุผลและเงื่อนไขที่จะเอากลับมา

ส่วนที่ 3 สำคัญที่สุดสำหรับการขาย เพราะมันตอบคำถามของผู้ซื้อว่า "เวอร์ชันที่เล็กที่สุด
ที่ยังเป็นเกมนี้อยู่ ราคาเท่าไร"

## 13 Risks

ตารางเรียงตาม **ผลกระทบ × โอกาสเกิด** ไม่ใช่ตามลำดับที่นึกออก

| ความเสี่ยง | ผลกระทบ | โอกาส | สัญญาณเตือนล่วงหน้า | แผนรับมือ |
|---|---|---|---|---|

ความเสี่ยงที่เอกสาร MMO ต้องมีเสมอ เพราะผู้ซื้อจะถามหา:
- เศรษฐกิจเฟ้อจนพัง / บอทฟาร์มเงิน
- จำนวนผู้เล่นไม่ถึงมวลวิกฤต ทำให้ระบบที่ต้องใช้คนหมู่มากตายทั้งระบบ
- ค่า server ต่อผู้เล่นสูงกว่ารายได้ต่อผู้เล่น
- ผลิตเนื้อหาไม่ทันการบริโภค
- The One Thing ไม่สนุกจริงตอนเอาไปทดสอบ (ความเสี่ยงที่ใหญ่ที่สุดเสมอ)

เอกสารที่เขียนความเสี่ยงตรงไปตรงมาน่าเชื่อถือกว่าเอกสารที่มองโลกสวย —
คนซื้อรู้อยู่แล้วว่าความเสี่ยงมี และกำลังดูว่าคนเขียนรู้ตัวหรือเปล่า
